# Adding a game

Every game is one self-contained JSON definition, `<gameId>.game.json`, following the canonical schema (`https://searchlight.jetlageuropa.org/schemas/game-definition.v1.schema.json`). The definition is the whole game: the app offers exactly the questions it declares (radar, thermometer and Station Name Length only when `radars`/`thermometer`/`stationNameLength` enable them, other matching/measuring/tentacles only from its `features` layers, plus players' own hand-drawn custom questions) and nothing is looked up in OSM/Overpass while playing.

The authoring guide is the game creation skill, `apps/web/public/skills/create-game.md` (served at `/skills/create-game.md`). It covers every field, how each layer type behaves in play, converting KML/GeoJSON/CSV/OSM data, the quality rules the validator doesn't enforce, and what `check-game.mjs` reports (its section 7). Its helper scripts are in `apps/web/public/skills/create-game/`.

## Steps

1. Build `<gameId>.game.json` following the skill.
2. Check it:

   ```bash
   node apps/web/public/skills/create-game/check-game.mjs --strict <gameId>.game.json
   pnpm --filter @searchlight/api validate-game <gameId>.game.json   # the server validator only
   ```

   `check-game.mjs --strict` fails on anything the import would reject and on the warnings that are always data defects, and prints the question list players will see.

   To see the file on a map, drop it on the import page, `/games/import` (see [below](#games-uploaded-by-game-devs)); it saves nothing until you click import.

3. Import it on the import page, as below. Locally (`pnpm dev`, see the [README](../README.md)), you can instead have the API import it on every start (see [Preloading](#preloading)).
4. In the browser, switch to the game and confirm the play area, the hiding-zone count and radii, and that each question in the check's list appears and evaluates.

## Preloading

With `GAMES_PRELOAD_DIR` set to a directory, `preloadGameDefinitions` (`apps/api/src/games/preload.ts`) imports every `*.game.json` in it whose content changed since the last API start (it remembers each game's file checksum), creating the game or adding a revision and making it current. Each file name must equal its definition's `id`, or the file isn't imported. Casual Games (`home-games`) files are refused too (`CASUAL_PRELOAD`): each Casual game belongs to whoever uploads it. Content identical to an older revision (e.g. a reverted file) re-activates that revision instead. A file unchanged since the last start leaves its game alone, so a revision uploaded or re-activated since stays current; the API then logs a warning such as `<gameId>.game.json is unchanged since the last start, but revision 2 was made current since; keeping 2`, counted as `kept` in the `Preloaded game definitions` line. A file that fails to import is logged at error level (`Failed to preload game definition; skipped`) and the other files still load. Removing a file deletes nothing. Unset, as in production, nothing is imported; [DEPLOY.md → Games](../DEPLOY.md#games) shows how to set it on a server.

## Games uploaded by game devs

Game devs don't need the repo. They build the file with the skill (an AI agent can do it from the announcement's rules doc and Google My Maps link, see its section 1.1) and upload it at `/games` → **+ Import Game JSON**, or with `POST /games/import`. The button opens the import page, `/games/import`, which draws the play area, the hiding zones and each layer on a map, shows `check-game.mjs`'s findings and the question list, can fix overlapping regions (see [Region overlaps](#region-overlaps)), and previews what the import will do before saving. A game file may be at most 10 MB as sent (the page sends it as compact JSON); a larger upload is refused with 413. Uploading needs a Discord role with `games.create` (new games) or `games.edit` (updates) on the game's server, or `server.admin`. A server admin grants these on `/admin` → **Manage Roles**. Casual Games needs no role (see [Casual Games](#casual-games)). Except for global admins (`ADMIN_DISCORD_IDS`), each player may upload, preview, change settings and create or revoke game links 60 times in 10 minutes, and run 2 uploads or settings changes at a time; more is refused with 429 `RATE_LIMITED`. If a game on that server already has the file's `id` (on Casual Games, one of your own games), the import page says it will update that game and compares the two: a different name or a play area that barely or doesn't overlap is flagged as a likely mistake, and the update then needs an extra confirmation. The page sends the id of the revision it previewed (`expectedCurrentRevisionId`), and the import is refused (409 `GAME_CHANGED`) if the game changed in between. The same `id` on another server, or in someone else's Casual games, is a separate game: the import creates a new one, and the page says so when you pick a server other than the file's. Where the id is taken on that server and you lack `games.edit`, the import is refused; give the file a new `id`. To replace one particular game with a file whatever its `id` and `serverId`, use **Replace with file…** on its row on `/games` (`POST /games/:gameId/import`). It needs the same permissions as an update, previews and confirms the same way, and the game keeps its own id and server. Games live in the database. Don't also put an uploaded game's file in the API's `GAMES_PRELOAD_DIR`: a file that differs from the upload replaces it on the next API start. Don't change a preloaded file's `serverId` either: the next start adds a second game on the new server and leaves the old one.

A preloaded game can also be updated by upload, including uploading an older version to roll it back. The upload stays current across restarts while the file is unchanged (see [Preloading](#preloading)). Once the file's content changes, the next start applies it and makes it current, replacing the upload, so carry an upload's fix into the file before changing it.

A game's name and size can also be changed on `/games` → **Settings** (needs `games.edit` or `server.admin`, or on Casual Games being the game's creator while in one of the JetLag Discord servers; `PATCH /games/:gameId/settings`). The change is saved as a new revision of the current definition, with `id` set to the game's ID so a rename can't turn it into another game, the same as uploading the edited file: sessions keep their revision until upgraded, the export has the new name, and for a preloaded game the next change to its file replaces it.

Deleting a game (`/games` → **Delete**, `DELETE /games/:id`) needs `games.delete`, or on Casual Games being the game's creator, also after leaving every server. The game disappears from `/games` and from the games offered for new sessions, its game links are revoked, and it can't be changed, exported or linked any more (those routes answer 404). Sessions already started, and sessions forked from them, keep playing their revision until their creators delete them; once the last one is deleted, the game is removed for good. Revisions no session uses are deleted at once. The game's id is free again: importing a file with it creates a new game. A deleted preloaded game is created again from its file on the next API start; remove the file from `GAMES_PRELOAD_DIR` to delete it for good.

**History** on a game's row on `/games` lists the game's entries in the audit log: who uploaded each revision and when, listing changes, and game links created or revoked. Whoever manages the game sees it (`GET /audit-log?serverId=…&targetId=<gameId>`). Revisions uploaded before the audit log existed are filled in from the stored revisions.

Exports and historical definitions are served only from the database, with access checks. Sessions load their pinned revision, and fork snapshots keep the revision captured with their questions. A session gives its participants access to that revision only; creating a session or upgrading it to the current revision needs the same server membership and role as reading the game.

A game can be **unlisted** (the **Unlisted** box on the import page for a new game, or **Make unlisted** on `/games`). Unlisted games aren't offered when creating a session, and nobody, game managers and admins included, can start a session of one directly: everyone plays them through a **game link**. Only `/games` lists them, for the server's game managers (`games.create`, `games.edit`, `games.delete` or `server.admin`), who alone may still read their definitions. Game links (`/games` → **Links**, for game managers) work for listed games too. A link lets whoever holds it start sessions of the game, without server membership or the role gate, until it is revoked; listing or unlisting the game doesn't affect it. A session started from a link can be upgraded to newer revisions while that link is active.

### Casual Games

**Casual Games** (formerly Home Games, server id `home-games` in game files) is for games outside the JetLag servers, such as a game among friends. It has no Discord server of its own: anyone in one of the registered Discord servers (those with a `Server` row) may create Casual games, without a role. Casual games are always unlisted, and only their creator and global admins see them on `/games`. The creator can update their game (by importing a file with its `id`, or with **Replace with file…**) and change its name and size with **Settings** while they are in one of those servers; they can export it, make game links for it and delete it also after leaving them all, and when the game's role gate names a role they lack. Global admins update anyone's Casual game with **Replace with file…** (their own import of the file creates a Casual game of their own), and delete anyone's. Each creator's games have their own ids, so two creators can use the same `id`. A Casual game imported before creators were recorded belongs to no one: only global admins reach it. Casual is never offered when creating a session: it only lists your existing sessions there, and every session of a Casual game starts from a game link, also for its creator.

Each player may have up to 20 Casual games (`CASUAL_GAME_LIMIT`; deleted ones don't count) taking up to 100 MB as stored (`CASUAL_STORAGE_LIMIT_MB`), counting every revision still stored, including those of deleted games that sessions still use. Creating a 21st game is refused with 409 `CASUAL_GAME_LIMIT`, and an import or settings change that would go over 100 MB with 413 `CASUAL_STORAGE_LIMIT`. Global admins have no limits. Casual games keep only the revisions still needed: the current one, the newest (so a revision number is never used twice), and those a session or an active session link still uses. The others are deleted whenever the game gets a new revision or is deleted, so content identical to a deleted revision is added again as a new one. Games on the other servers keep all their revisions while they aren't deleted.

## Region overlaps

Neighbouring regions in a layer (provinces, boroughs) should share their borders exactly. Traced or simplified independently, they often overlap in slivers instead. A player in an overlap is in the first of its regions in file order, both for matching answers and for measuring to their own region's boundary.

The import page checks every region layer for overlaps, ignoring hairlines that reach less than 0.5 m into a region. For each layer it shows how many overlaps there are, their total area, how far the widest reaches, and how many hiding zones reach into one, and it can draw them on the map (**Show**). It ticks every layer it can fix or mark, and **Fix overlaps and mark** gives each overlap to the first region, as the app already does: each region loses what the regions before it cover, where it overlaps them by more than a hairline (regions that only touch are left as they were). So players stay in the regions they were in, and a distance to a border moves by at most the overlap's width. New corners are rounded to the layer's precision, but to no fewer than 6 decimals (about 0.1 m). A layer with a region entirely inside earlier ones (less than 1 m² of it left) can't be fixed: no one is ever in that region, so remove it or move it before them.

A fixed layer, or one without overlaps that you mark (**Mark … noOverlaps**), gets `"noOverlaps": true`. Without overlaps, the border of the region a player is in is also the nearest border of any region, so the app can answer "Distance to {name} Boundary" with one buffer around the whole border network. Download the changed file from the page to keep your copy in step: importing the old copy again undoes the fix. Nothing on the server checks the mark, so a file edited after it was marked, or marked by hand, could still overlap: the import page refuses to import a marked layer that overlaps until it is fixed (or, if it can't be, its mark removed with **Remove mark**), and `check-game.mjs --strict` fails on one whose regions' borders reach more than 0.5 m into another region.

For files on disk, `pnpm fix:region-overlaps <files>` makes the same fix and marks every region layer without overlaps.
