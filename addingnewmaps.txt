HOW TO ADD A NEW MAP
====================

1. GET THE CORRECT OSM RELATION ID
   Look up the city on Nominatim to get the right OSM relation ID:
   https://nominatim.openstreetmap.org/search?city=CITYNAME&country=COUNTRY&format=json&limit=3

   Check the "osm_type" (should be "relation") and "osm_id" in the response.
   Also grab the "boundingbox" values — they go in the extent field (order: north, west, south, east).

   Do NOT guess the OSM ID — wrong IDs silently return empty and break the map boundary load.


2. PLACE THE PUBLIC ASSET FILES
   Copy files to apps/web/public/. Naming convention: lowercase, hyphens, no spaces.

   STANDARD GAME (one KML for stations/hiding zones):
     apps/web/public/<cityname>-hiding-zones.kml

   GAME WITH SEPARATE STATION FILE + POI OVERRIDES (e.g. Brno 2026 v2):
     apps/web/public/<cityname>-stations.kml     ← Point placemarks only, used for hiding zones
     apps/web/public/<cityname>-poi.kml          ← Folder-organised POI placemarks

   The stations KML must only contain <Point> placemarks. Lines and polygons
   are silently ignored by the parser. If your KML has both points and zone
   outlines (e.g. exported from Google My Maps), it still works — only the
   Point features are loaded as stations.

   The POI KML must organise placemarks into <Folder> elements. Each folder's
   <name> is mapped to a category (see step 4b). Folders with categories
   "administrative" or "water" are skipped.


3. ADD THE GAME TO seed.ts
   File: apps/api/prisma/seed.ts

   a) Add a city feature constant above the GAMES array:

      const CITYNAME_CITY_FEATURE = {
        type: "Feature",
        geometry: {
          type: "Point",
          coordinates: [LAT, LON],        // from Nominatim lat/lon fields
        },
        properties: {
          osm_type: "R",
          osm_id: 123456,                 // from Nominatim osm_id
          extent: [NORTH, WEST, SOUTH, EAST],  // from Nominatim boundingbox
          country: "Country Name",
          osm_key: "place",
          countrycode: "XX",              // ISO 3166-1 alpha-2
          osm_value: "city",
          name: "City Name",
          type: "city",
        },
      };

   b) Add an entry to the GAMES array:

      STANDARD (kmlPath is the hiding zones file):
      {
        serverId: "DISCORD_SERVER_ID",    // see SERVERS list at top of seed.ts
        name: "City Name YYYY",
        sentinelValue: "__bundled-cityname-yyyy__",  // must be unique
        kmlPath: "cityname-hiding-zones.kml",
        mapLocationJson: CITYNAME_CITY_FEATURE,
        hidingRadius: 400,               // default radius for all stations
        hidingRadiusUnits: "meters",     // "meters" or "kilometers"
      },

      WITH SEPARATE STATIONS + POI (kmlPath is the POI file):
      {
        serverId: "DISCORD_SERVER_ID",
        name: "City Name YYYY",
        sentinelValue: "__bundled-cityname-yyyy__",
        kmlPath: "cityname-poi.kml",     // POI data — NOT the stations
        mapLocationJson: CITYNAME_CITY_FEATURE,
        hidingRadius: 400,
        hidingRadiusUnits: "meters",
      },

      When using separate stations + POI, kmlPath holds the POI KML. The
      stations KML is wired up client-side in step 4 (no DB change needed).

   c) PER-TIER RADIUS OVERRIDES (optional)
      If different station types need different hiding zone sizes, add
      tierRadiusOverrides to the game entry. The keys must exactly match
      the tier values stored in the KML's <Data name="tier"> ExtendedData
      fields. Values are in the same units as hidingRadiusUnits.

      Example — Utrecht 2026 (Train: 400 m, Tram/Bus: 250 m):

        hidingRadius: 250,               // fallback for any station with no override
        hidingRadiusUnits: "meters",
        tierRadiusOverrides: { Train: 400 },

      How it works:
      - When the hiding zones are generated, each station's tier is read
        from its KML <Data name="tier"> field.
      - If that tier has an entry in tierRadiusOverrides, that value is
        used for the circle radius instead of hidingRadius.
      - Stations with no tier, or a tier not in the overrides map, fall
        back to hidingRadius.
      - The radius slider in the UI only affects stations that use the
        fallback hidingRadius — overridden tiers are always fixed.

      KML tier format (Google My Maps ExtendedData):

        <ExtendedData>
          <Data name="tier">
            <value>Train</value>
          </Data>
        </ExtendedData>

      If your KML has no tier data, omit tierRadiusOverrides entirely (or
      set it to null) and all stations will use hidingRadius.

   Server IDs:
     JetLag EU  — 1190673594649415730
     JetLag UK  — 1059625399979606166
     JetLag BNL — 1369664929975767120
     JetLag DE  — 1333139120507064350


4. CLIENT-SIDE WIRING (for separate stations + POI only)
   File: apps/web/src/lib/games.ts

   Standard games need no changes here — kmlPath is used automatically.

   For games with a separate stations KML and/or POI overrides, add entries
   to the client-side constant maps keyed by sentinelValue.

   a) SEPARATE STATIONS KML
      Add to GAME_HIDING_ZONE_KML_PATHS:

        const GAME_HIDING_ZONE_KML_PATHS: Record<string, string> = {
          "__bundled-cityname-yyyy__": "cityname-stations.kml",
        };

      When this is set, the stations KML is fetched instead of kmlPath for
      hiding zones. kmlPath is then used exclusively for POI data (step 4b).

   b) POI FOLDER → CATEGORY MAPPING
      Add to GAME_KML_POI_FOLDERS:

        const GAME_KML_POI_FOLDERS: Record<string, Record<string, string>> = {
          "__bundled-cityname-yyyy__": {
            "FolderName1": "museum",
            "FolderName2": "train_station",
            "FolderName3": "airport",
            "FolderName4": "park",
            "FolderName5": "hospital",
            "FolderName6": "library",
            "FolderName7": "theme_park",
            "FolderName8": "zoo",
            "FolderName9": "golf_course",
            "FolderName10": "cinema",
            "FolderName11": "administrative",  // skipped
            "FolderName12": "water",           // skipped
          },
        };

      The keys are the exact <name> text of each <Folder> in the KML.
      Supported category values and what they override:

        museum        — "Same museum?" matching question
        train_station — station-name questions (same first letter, same length, same line)
        airport       — "Same airport?" matching + tentacle airport
        park          — "Same park?" matching question
        hospital      — "Same hospital?" matching question
        library       — "Same library?" matching question
        theme_park    — "Same theme park?" matching question
        zoo           — "Same zoo?" matching question
        golf_course   — "Same golf course?" matching question
        cinema        — "Same cinema?" matching question
        administrative — skip (no question type uses this)
        water          — skip (no question type uses this)

      When a game has POI data for a category, ALL Overpass API queries for
      that category are replaced with the custom data while that game is
      active. Switching to a different game clears the POI cache.

      Single-POI categories (e.g. one airport) work fine — the Voronoi
      single-point edge case is handled automatically.


5. RUN THE SEED
   The API Docker image does not include tsx (dev dependency), so
   `prisma db seed` does NOT work inside the container. Use raw SQL instead.

   Dev DB (via docker exec):

     docker exec writemap-dev-postgres-1 psql -U taibled -d taibled -c "
     INSERT INTO \"Game\" (id, \"serverId\", name, \"sentinelValue\", \"kmlPath\",
       \"mapLocationJson\", \"hidingRadius\", \"hidingRadiusUnits\", \"updatedAt\",
       \"tierRadiusOverrides\")
     VALUES (
       gen_random_uuid()::text,
       'DISCORD_SERVER_ID',
       'City Name YYYY',
       '__bundled-cityname-yyyy__',
       'cityname-poi.kml',
       '{...mapLocationJson object as JSON string...}',
       400,
       'meters',
       NOW(),
       NULL
     )
     ON CONFLICT (\"sentinelValue\") DO UPDATE
       SET name = EXCLUDED.name, \"updatedAt\" = NOW();
     "

   Live DB: same command but use writemap-postgres-1.

   Note: ON CONFLICT only updates the name. To fix other fields after
   inserting, see step 6.


6. FIXING A FIELD AFTER SEEDING
   If you seeded with wrong values, update directly:

     DATABASE_URL="postgresql://taibled:devpassword@localhost:5433/taibled" \
       node --import tsx/esm -e "
     import { PrismaClient } from '@prisma/client';
     const prisma = new PrismaClient();
     await prisma.game.update({
       where: { sentinelValue: '__bundled-cityname-yyyy__' },
       data: { hidingRadius: 400, hidingRadiusUnits: 'meters' },
     });
     await prisma.\$disconnect();
     "

   Also clear any stale boundary cache if you had a wrong OSM ID:

     await prisma.boundaryCache.deleteMany({ where: { osmId: 'WRONG_ID' } });


7. TEST BEFORE COMMITTING
   Load the map in the browser and confirm:
   - The city boundary loads without error
   - The hiding zones appear correctly
   - The hiding radius looks right on the map
   - If using tierRadiusOverrides: visually confirm that overridden tiers
     have larger/smaller circles than the default, and that moving the
     radius slider does NOT change the overridden circles.
   - If using POI overrides: open browser console and confirm log lines like
       [taibled:poi] loaded custom POI for City Name museum:20, park:58, ...
     Then test a matching question for each category — it should NOT trigger
     an Overpass request.
   - If using a separate stations KML: confirm the console shows
       [taibled:stations] loaded N stations from cityname-stations.kml for City Name
     and that the correct number of hiding zone circles appear.

   Then commit and push (dev first, then replicate to live).
